Suppose an agent flags a colleague for missing a deadline, citing the original commitment and its date. You find a later message agreeing to move the deadline.

In this hypothetical case, the agent remembered a true statement but failed to establish which agreement still applied. A commitment checker needs enough context to find the changed deadline and rules for deciding what counts as evidence.

## Three different jobs

Memory supplies context: a promise, a conversation, an earlier decision.

Evaluation assesses an outcome: whether the applicable promise was fulfilled, whether the evidence is sufficient, and how uncertain the conclusion remains.

Authorization constrains action: whether the system may send an alert, edit a record, or contact someone.

A system can remember the right promise, evaluate it incorrectly, and still be prevented from sending anything. It can also evaluate an outcome correctly while lacking permission to act on it. Improving its memory, for example, leaves both evaluation and permissions to be tested.

I would test the meeting's proposed contradiction checker against one narrow expectation first. We need to see what it gets wrong before deciding where it belongs in an organization.

## Write a rule you can disagree with

Consider this illustrative rule: flag a deliverable as potentially overdue when its current agreed deadline has passed and there is no recorded completion evidence.

To implement that rule, we need to settle several questions. What makes a deadline agreed? Which source wins when dates conflict? Does a cancellation remove the obligation? Does missing evidence mean the work was not done, or that the system cannot see it?

A proposed check might return one of five states: fulfilled, potentially overdue, rescheduled, cancelled, or insufficient evidence. Each judgment should carry the source passages or records used to reach it. The checker should be able to return insufficient evidence when the records do not support a decision.

Then give the checker examples. Include a straightforward breach, a completed task, a changed deadline, a cancellation, and a task finished in a system the agent cannot access. Have people judge these before relying on the agent's classifications.

If people disagree, check the rule: it may never have specified whether an informal message could change a deadline.

## The checker needs checking

[EvalGen research](https://people.eecs.berkeley.edu/~bjoern/papers/shankar-validators-uist2024.pdf), presented at UIST 2024, explores helping users generate evaluation criteria and implementations, then using human ratings to align evaluators with those judgments. The researchers describe criteria drift: inspecting examples can change what people believe the criterion should mean.

As people revise their criteria, they need to retest the implementations, including any generated by a model.

[Anthropic's evaluation guidance](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) distinguishes code-based, model-based, and human grading, and separates recorded interactions from actual outcomes. An exact field requirement can be checked directly. Whether an explanation adequately accounts for conflicting evidence may need judgment and calibration.

Our commitment checker would probably use both. A deterministic check can compare a timestamp with a known deadline. A model might interpret a conversation proposing a change. That interpretation should not acquire certainty just because it feeds a precise date comparison.

## Check the world after the action

The original [τ-bench research](https://arxiv.org/abs/2406.12045) evaluates agents in part through final database states and repeated trials. That gives us a way to compare what the agent says it completed with what it actually changed.

If the task was to update a record, inspect the record. If it was to create a proposal, inspect the proposal and its relationship to the requested change. Repeating the task can also reveal inconsistency hidden by one successful run.

A correct final state still does not establish a safe process. An agent might reach it while accessing information it should not use or taking an unauthorized intermediate action. Outcome checks and action constraints answer different questions.

[Open Policy Agent](https://www.openpolicyagent.org/docs) makes the architectural distinction explicit: deciding what policy permits is separate from enforcing that decision. The application has to apply the restriction. Asking the agent to remember a rule cannot provide the same guarantee.

## Begin with observation

For a commitment checker, I would start with proposed alerts that remain visible only to the authorized reviewer. Record false alarms and missed cases, including the cost of investigating an alert. Keep disputed examples so revisions can be tested against them.

Only after that calibration would I consider an external action, with its own authorization boundary. A wrong private suggestion and a wrong message accusing someone of breaking a commitment have very different consequences.

For the first rule, write down what would count as fulfillment and which exceptions could change the judgment. Give people examples where the evidence is incomplete, then compare their decisions with the checker's.
